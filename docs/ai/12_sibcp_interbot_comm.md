# 12 — SIBCP Inter-Bot Communication

## Scope

The firmware now implements an experimental transport bridge for robot-to-robot data:

```
robot MCU -- UART1 or USB-C/SIBCP -- local module -- ESP-NOW broadcast -- peer module -- UART1 or USB-C/SIBCP -- peer robot MCU
```

The module does **not** implement a topic registry, service dispatcher, retry layer, or
application-level routing. It validates SIBCP frames, moves valid frames between UART1 or
USB-C and ESP-NOW, mirrors received frames to local serial outputs, and emits bounded BLE
debug logs.

Application code can use the Python helper package in `python/sibcp` to define path-based
topics and services on top of this transport. The package keeps the wire format compact:
paths such as `/ball_in_your_vision` are local names that both robots map to the same
numeric identifier.

## Hardware transport

| Link | Configuration |
|------|---------------|
| Robot MCU to module | UART1, `RX1=IO4`, `TX1=IO5`, `INTERBOT_UART_SPEED=460800` |
| USB host to module | USB Serial/JTAG, usually `/dev/ttyACM0`; baud setting ignored by USB |
| UART0 output mirror | `TX0`, 115200 baud, transmit-only SIBCP output mirror |
| Module to module | ESP-NOW broadcast, station mode, 5 GHz only, channel 36 |
| BLE debug logs | NUS service, extra notify characteristic `6E400004-B5A3-F393-E0A9-E50E24DCCA9E` |

`interbot_comm_init()` starts UART1, consumes USB Serial/JTAG bytes through `serial_status`,
and configures Wi-Fi station mode with sleep disabled.
If 5 GHz support or ESP-NOW setup fails, UART parsing still runs but frames are not sent over
radio (`interbot_ready=false`).

## Frame format

Defined in `sibcp_protocol.h`:

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | start byte `0xAA` |
| 1 | 1 | start byte `0x55` |
| 2 | 1 | packet type |
| 3 | 2 | transaction id, little-endian `uint16_t` |
| 5 | 1 | identifier id |
| 6 | 2 | payload length, little-endian `uint16_t` |
| 8 | N | payload |
| 8+N | 2 | CRC-16/CCITT, little-endian |

CRC is computed over byte 2 through the end of the payload, not including the two magic
bytes and not including the CRC field. Polynomial is `0x1021`, initial value `0xFFFF`.

Packet types currently named by firmware:

| Value | Name |
|-------|------|
| `0x01` | topic |
| `0x02` | service request |
| `0x03` | service response |
| `0x04` | service discovery |

Example identifiers are reserved for initial testing:

| Value | Meaning |
|-------|---------|
| `0x01` | `SIBCP_TOPIC_ROBOT_NUM` |
| `0xF0` | `SIBCP_TOPIC_SYSTEM_GAME_STATE` |
| `0x01` | `SIBCP_SERVICE_ADD_THREE` |

The reserved system game-state topic is emitted locally by the module when referee state
changes. It is not generated by the peer robot:

| Field | Type | Meaning |
|-------|------|---------|
| `state` | `uint8_t` | `0` init, `1` disconnected, `2` play, `3` stop, `4` damage, `5` half-time, `6` game-over |
| `robot_play` | `uint8_t` bool | `1` means output pins are HIGH / robot may play, `0` means stopped |

## Payload size

`SIBCP_MAX_PAYLOAD_LENGTH` is 240 bytes. With the 8-byte header and 2-byte CRC, this keeps
the full SIBCP frame at 250 bytes, matching the conservative ESP-NOW v1 payload limit.

## Runtime behavior

- UART1 and USB-C bytes are parsed with separate streaming parsers that resynchronize on
  `0xAA 0x55`.
- Only fully valid SIBCP frames are forwarded.
- UART1 -> ESP-NOW and USB-C -> ESP-NOW frames are sent to the broadcast peer.
- ESP-NOW frames are revalidated before writing raw frame bytes to UART1, USB-C, and the
  UART0 TX mirror.
- Local referee state changes are emitted as `TOPIC id=0xF0` frames on UART1, USB-C, and
  the UART0 TX mirror.
- Radio receive and BLE debug logging use bounded FreeRTOS queues with drop-oldest behavior
  for debug logs.
- Debug log lines look like:

```text
[SIBCP UART->NOW] SRV_REQ id=1 tx=402 len=24
[SIBCP USB->NOW] SRV_REQ id=1 tx=402 len=24
[SIBCP NOW->HOST] SRV_RES id=1 tx=402 len=9
[SIBCP SYS->HOST] TOPIC id=240 tx=0 len=2
```

## Python client library

The Python package lives in `python/sibcp` and can be installed from the repository root:

```sh
python -m pip install -e python/sibcp[serial]
```

Minimal service responder:

```python
from sibcp import Bool, SerialTransport, SibcpNode

node = SibcpNode(SerialTransport("/dev/ttyACM0", baudrate=460800))
node.service("/ball_in_your_vision", service_id=1, response=Bool)

@node.on_service("/ball_in_your_vision")
def handle_ball_request(_request):
    return camera.sees_ball()

node.start_background_reader()
```

Minimal caller:

```python
from sibcp import Bool, SerialTransport, SibcpNode

node = SibcpNode(SerialTransport("/dev/ttyAMA0", baudrate=460800))
node.service("/ball_in_your_vision", service_id=1, response=Bool)

peer_sees_ball = node.call("/ball_in_your_vision", timeout=0.2)
```

Supported built-in codecs include `Bool`, fixed-width signed/unsigned integers, `Float32`,
`String`, `Bytes`, and ordered `Struct` payloads. Service response frames add a leading
status byte (`0` success, `1` handler error, `2` unsupported service) before the encoded
response value.

System game-state monitoring:

```python
from sibcp import (
    GameState,
    SerialTransport,
    SibcpNode,
    SYSTEM_GAME_STATE_TOPIC,
    define_system_topics,
)

node = SibcpNode(SerialTransport("/dev/ttyACM0", baudrate=460800))
define_system_topics(node)

@node.on_topic(SYSTEM_GAME_STATE_TOPIC)
def handle_game_state(message):
    state = GameState(message["state"])
    robot_play = message["robot_play"]
```

## Current limitations

- Broadcast only; no per-peer addressing or duplicate filtering.
- No ACK, retry, congestion control, encryption, or authentication.
- No service discovery response generation inside the module.
- No runtime channel configuration; channel 36 is compiled in.
- Two-module communication is the intended first test case. More than two modules will need
  addressing and duplicate handling before match use.
